Welkom bij je maandelijkse dosis cybersecurity.

Meestal kijk je in deze nieuwsbrief mee met de aanvaller. Deze keer sta je aan de andere kant van de deur: bij het bestand waarin een server zelf bijhoudt wie er heeft aangeklopt. Dat bestand mag je gewoon lezen.

Tip van de maand

Een server schrijft alles op

Een Linux-server schrijft mee. Niet omdat iemand dat heeft aangezet, maar omdat het standaard gebeurt: elke keer dat iemand probeert in te loggen, komt er een regel bij in een logbestand. Een dagboek dat de server over zichzelf bijhoudt, zonder dat er iemand naar kijkt.

Je hoeft zo'n bestand niet te begrijpen om erin te kunnen kijken. Je moet alleen weten waar het staat, en dat is op Linux altijd dezelfde plek: de map /var/log. Ga erheen en kijk wat er ligt:

$ cd /var/log
$ ls

auth.log  syslog

Twee bestanden, en de eerste is de interessante. De auth in auth.log staat voor authentication: wie zich heeft aangemeld, en of dat lukte. Open het:

$ cat auth.log

10:23:45 Accepted password
   for hacker from
   192.168.1.50
10:25:12 Failed password
   for root from 10.0.0.99
10:25:15 Failed password
   for root from 10.0.0.99
10:25:18 Failed password
   for root from 10.0.0.99
10:25:20 Connection closed
   by 10.0.0.99

Vijf regels, en samen vertellen ze een verhaal. Bovenaan logt hacker zichzelf in vanaf 192.168.1.50 — Accepted, gelukt. Daarna probeert iemand vanaf een heel ander adres, 10.0.0.99, het wachtwoord van root — het account dat op een Linux-systeem alles mag. Failed, drie keer achter elkaar. En dan gaat de verbinding dicht.

Kijk nu naar de klok: 10:25:12, dan 10:25:15, dan 10:25:18. Precies drie seconden ertussen. Iemand die zijn eigen wachtwoord vergeten is, typt onregelmatig, vloekt een keer en probeert het twee minuten later nog eens. Dit ritme hoort bij een programma dat een lijst met wachtwoorden afwerkt. De inhoud van de regels vertelt je wat er gebeurde. Het tempo vertelt je wie het deed.

(Wat je op je scherm ziet is iets voller dan hierboven: op elke logregel staan ook nog een datum, de naam van de server en een poortnummer, de simulator zet er zelf nog een hint onder, en cd meldt bij hem dat de map gewijzigd is terwijl een echte terminal daar zwijgt. Ik heb dat hier weggelaten — anders past één logregel niet eens in je mail.)

Dit oefenbestand heeft vijf regels, dus je ziet het verhaal in één oogopslag. Een echte server schrijft er duizenden per dag, en dan werkt scrollen niet meer. Daarvoor is grep. Waar ls je laat zien welke bestanden er zijn, kijkt grep in een bestand. En je weet inmiddels welk woord je zoekt — een mislukte poging heet hier Failed:

$ grep Failed auth.log

2: 10:25:12 Failed password
   for root from 10.0.0.99
3: 10:25:15 Failed password
   for root from 10.0.0.99
4: 10:25:18 Failed password
   for root from 10.0.0.99

Dezelfde drie regels, nu zonder de rest eromheen. Het getal vooraan is het regelnummer in het bestand, zodat je ze terugvindt — en dat klopt precies: regel 1 was de geslaagde login van hacker, dus de mislukte pogingen staan op 2, 3 en 4.

Dat is monitoring in zijn kortste vorm. Geen dashboard, geen abonnement: een bestand dat er toch al stond, en één goede zoekterm.

Probeer het zelf: Open de simulator en typ cd /var/log, dan ls, dan cat auth.log en tot slot grep Failed auth.log. Kijk daarna zelf eens wat grep Accepted auth.log oplevert.

En op je eigen computer?

Draai je zelf Linux? Dan heb je zo'n bestand ook — op Ubuntu en Debian meestal als /var/log/auth.log, op andere distributies onder een andere naam of via journalctl. Je hebt er sudo voor nodig, want het logbestand is niet voor iedereen leesbaar. Kijken kun je dus meteen — en de vier commando's hierboven zijn geen simulator-taal: cd, ls, cat en grep typ je op een echte Linux-machine precies zo.

Wat je thuis niet hebt is een doelwit waar je op mag oefenen — en zonder aanvalskant zie je nooit hoe die regels in je log terechtkomen. Daar is een eigen lab voor.
